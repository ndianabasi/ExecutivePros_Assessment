# Mock Payment Provider Service Implementation Document

## 1. Purpose and boundary

This document specifies only the **Mock Payment Provider Service** in [System_Architecture.md](System_Architecture.md). The service accepts API-initialised payment transactions, renders a browser checkout page, records the authoritative **simulated provider** outcome, and sends signed webhook events to the API Service. The API Service owns carts, its own payment record, verification, fulfilment, reconciliation, SSE, and notifications. The frontend hosts the provider page in an iframe and treats its completion message only as a prompt to fetch API state.

The target is a trusted, host-local assessment demo. There is one provider Node.js container and one provider-owned SQLite file, `payment_provider.db`. Workmatic stores its persistent webhook jobs **in that same file**, as the architecture requires. No provider endpoint grants API-side value or manually changes an API payment status.

### Settled decisions and architecture clarification

| Area | Decision |
| --- | --- |
| Route naming | `POST /payments/initialise` is the authenticated API-to-provider creation route. The provider-rendered browser page calls `POST /payments/submit` for Pay, Fail, or Cancel. These replace the architecture's ambiguous `POST /payments` wording. |
| Status lookup | The API may call a read-only, service-authenticated `GET /payments/:reference` to recover an uncertain initialization or reconcile a missed webhook. It is not a payment-confirmation or status-mutation endpoint. |
| Browser authority | The `payment_url` contains a cryptographically random, opaque checkout capability token. A payment reference alone cannot complete a transaction. |
| Expiry | The API supplies one immutable `checkout_expires_at` cutoff. The provider rejects a new browser completion after it but leaves a still-pending provider payment pending for the API's day-30 lookup. |
| Outcome selection | The page offers Pay, Fail, and Cancel. `WEBHOOK_008` is Pay-only; its provider truth remains success while a later failed event tests API conflict handling. |
| Scenarios | Active failure scenarios are idempotently seeded and discoverable, not editable through runtime admin routes. `PROVIDER_001` delays before persistence. The lost-response-after-creation case is exercised by a test proxy, not a seeded scenario. |
| Failed delivery | Retain failed webhook events, attempt records, and Workmatic jobs for inspection. There is no manual replay route or dashboard; API status reconciliation is the normal recovery path. |
| Late success | Browser checkout expires at the agreed cutoff. An isolated test fixture, never a runtime mutation route, verifies the API's defensive late-success discrepancy handling. |

## 2. Workspace, persistence, and startup

Create one strict TypeScript/Node.js Yarn workspace with Express, VineJS validation, Knex migrations, parameterized `knex.raw` runtime SQL, Workmatic, and Pino. Keep configuration, API-authenticated routes, checkout rendering/submission, provider repositories, scenario resolution, webhook outbox/worker, and logging separate. Provide `lint`, `typecheck`, `test`, `test:unit`, `test:integration`, `test:contract`, `test:e2e`, and `build` scripts. Use one Dockerfile and one service container.

Use a persistent local-volume `PROVIDER_DB_PATH=/data/payment_provider.db`. Keep the architecture's `payments`, `webhook_events`, `webhook_deliveries`, and `failure_scenarios` tables, with their unique references/event IDs, foreign keys, status checks, and timestamps. Add to provider payments a unique provider reference, a SHA-256 checkout-token hash, immutable payment URL and expiry, and a snapshot of the selected scenario code/configuration. Keep the URL retrievable for idempotent initialization and API recovery; protect it as a bearer capability in logs, error responses, and backups. Generate 256-bit random tokens and provider references with cryptographic randomness. A unique reference plus an immutable fingerprint of amount, currency, expiry, and selected scenario decides initialization replay versus `409` conflict.

The provider payment status (`pending`, `success`, `failed`, `cancelled`) is separate from webhook event status (`pending`, `delivering`, `delivered`, `failed`, `skipped`) and attempt status. Store the original canonical event body immutably in `webhook_events`. In `webhook_deliveries`, store a distinct atomic attempt number, request-body hash or transmitted bytes needed to audit malformed/modified scenarios, bounded/redacted HTTP response text, status code, timing, and error class. Add event dispatch claim/lease and Workmatic-job correlation fields as needed. Index pending dispatch/expiry scans, `(payment_id, created_at)`, and `(webhook_event_id, attempt_number)`; enforce unique attempt numbers per event. Retain completed, failed, skipped, and Workmatic `done`/`dead` records until an explicit disposable-volume reset. Do not write another service's database.

Knex owns provider-domain migrations and seeds. Use Knex's schema builder only in migrations; provider runtime domain queries use named-binding `knex.raw`. Workmatic owns its own tables through `createDatabase()` in the **same file** and is the deliberate exception to the Knex-only query rule; do not query or migrate its tables with Knex. Pass Workmatic an existing configured `better-sqlite3` connection so its connection also has foreign keys, WAL, and a finite busy timeout. Run provider `up` migrations and idempotent seeds, then initialize/validate Workmatic tables before listening. The root Commander deployment migration flow invokes the provider's prestart steps. Production `down` migrations are disallowed. Verify pragmas and expected schema at startup. Retry an entire safe transaction on bounded `SQLITE_BUSY`, never a partial statement sequence. Never hold a SQLite write transaction across a timer or HTTP call. [Workmatic supports an existing `better-sqlite3` connection and documents at-least-once leases.](https://github.com/litepacks/workmatic)

Validate `NODE_ENV`, `PORT`, `PROVIDER_DB_PATH`, `PROVIDER_PUBLIC_ORIGIN`, `FRONTEND_ORIGIN`, `API_WEBHOOK_URL`, `PROVIDER_SERVICE_SECRET`, and `PROVIDER_WEBHOOK_SECRET` before startup. Secrets come from runtime environment or mounted secret files, not code, images, seeds, runtime browser config, URLs, or logs. `API_WEBHOOK_URL` is a fixed configured internal `/v1/webhooks/payment` target, never client supplied. `PROVIDER_PUBLIC_ORIGIN` is a browser-reachable host-loopback origin; the API uses the provider's Compose hostname for server calls. Reject invalid origins, weak/missing secrets, and a database path outside the mounted directory. Start in order: migrations/seeds, Workmatic initialization, event-dispatch sweep, worker registration/start, then HTTP listener. Stop accepting requests on SIGTERM/SIGINT, drain bounded in-flight work, and leave events/jobs restartable; do not persist a paused worker state.

## 3. HTTP and browser contracts

Service routes require `Authorization: Bearer <PROVIDER_SERVICE_SECRET>` with safe comparison; do not accept user Bearer tokens on them. Use VineJS to validate JSON bodies, paths, and scenario codes. Return sanitized errors with request ID; never echo tokens, signatures, full URLs, or stack traces. Do not enable browser CORS on server routes.

| Route | Access and behavior |
| --- | --- |
| `POST /payments/initialise` | API-only. Accept `{reference, amount, currency: "NGN", checkout_expires_at, failure_scenario_code?}`. Validate a safe unique reference, positive safe-integer minor-unit amount, future bounded UTC cutoff **on creation**, supported currency, and active scenario. Check for an exact existing-reference replay before rejecting a cutoff that has since passed. Return `201` on creation or `200` with the same provider reference, status, URL, and cutoff for an identical replay. Return `409` for same-reference/different-details, `422` for invalid domain fields, `401` for bad service auth, and `503` for transient storage failure. |
| `GET /payments/:reference` | API-only, read-only. Return reference, provider reference, amount, currency, authoritative provider status, payment URL when created, and cutoff; return `404` until initialization actually persists a record. Never perform or confirm a payment from this route. |
| `GET /failure-scenarios` | API-only. Return active scenario code, name, description, and category in stable code order; do not expose secret configuration or an edit action. |
| `GET /checkout/:token` | Browser capability route. Validate token hash and render a no-store payment page showing trusted amount, currency, reference, selected scenario, and allowed actions. Show an expired state after the cutoff and the existing outcome after completion. |
| `POST /payments/submit` | Browser capability route called by the provider page. Accept a bounded form submission containing only `checkout_token` and `outcome` (`success`, `failed`, `cancelled`). Invalid token returns `404`; a pending payment after cutoff returns `410`; a conflicting terminal outcome returns `409`. Repeat submission of the same completed outcome shows the prior result without another event. |
| `GET /health/live`, `GET /health/ready` | Internal probes. Readiness requires valid configuration, expected provider and Workmatic schemas, a writable database, and a running worker. API webhook outage is logged but does not make the provider unready while it can durably record outcomes and jobs. |

For `PROVIDER_001`, wait 30 seconds **before** writing the provider transaction. Multiple timed-out same-reference calls must converge on one row; status lookup may return `404` until a call commits. Do not cancel the delayed initialization solely because the API disconnected. `PROVIDER_002` returns the seeded HTTP `500` without creating a provider payment. The API treats that `500` as transient. A response-lost test proxy drops a successful initialization response **after commit**; the API recovers the same row by lookup/replay.

The checkout page is a provider-origin page within the frontend iframe, with a standalone-tab fallback. Use native, labelled form actions, keyboard focus, readable status text, no card-number collection, and no third-party assets. The browser submission uses the token, not API user credentials. Commit payment status, `completed_at`, immutable event(s), and dispatch intent in one database transaction **before** returning the completion page. A provider completion is independent of webhook acknowledgment. Send `postMessage({ type: 'mock-payment.finished', reference })` only to exact `FRONTEND_ORIGIN` from the resulting page when framed; omit status and tokens. A standalone tab shows instructions to return to the frontend and refresh. Set `Content-Security-Policy` with `frame-ancestors` for the frontend origin, `script-src 'self'`, and only required same-origin connections; omit a conflicting `X-Frame-Options` restriction. Set `Cache-Control: no-store` and `Referrer-Policy: no-referrer` on token-bearing pages. Do not log raw token paths. [The frame-ancestor policy controls who may embed the page.](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors)

## 4. Webhook outbox, delivery, and scenario behavior

Each terminal provider outcome creates at least one durable event with a stable, unique `event_id`, type (`payment.success`, `payment.failed`, `payment.cancelled`), and body containing `event_id`, event type/status, reference, provider reference, amount, currency, and occurrence time. Serialize a body once; sign the **exact transmitted bytes** with HMAC-SHA-256 using `PROVIDER_WEBHOOK_SECRET`, in `X-Provider-Signature: sha256=<hex>`. Reuse event ID and body for retries. No signature secret appears in the body or logs. Restrict outbound delivery to the configured internal API URL, send a request ID for correlation, set a bounded body/response size and HTTP timeout, and never follow an arbitrary redirect. The API's `2xx` is acknowledgment; provider status does not depend on it.

Treat `webhook_events` as a durable outbox. After the outcome transaction commits, a bounded sweeper claims due events and calls Workmatic `client.add()` for the `webhooks` queue in the same provider DB. Store job correlation/claim state after enqueue. If the process crashes before enqueue, the event remains discoverable; if it crashes after enqueue but before recording correlation, another job can be created and the API must deduplicate by event ID. Recover expired claims after restart. Workmatic owns job leases/retry timing; keep all provider-state changes in provider-domain SQL. Do not expose Workmatic's dashboard or job-management routes.

Configure five total Workmatic delivery **rounds** with 2-, 4-, 8-, and 16-second backoff, a bounded HTTP timeout shorter than job timeout, and a lease longer than job timeout. A duplicate scenario may issue two or three HTTP submissions within one round. Retry a round when no submission received `2xx` and at least one failed through a network error, timeout, `5xx`, `408`, or `429`. Stop after a `2xx` acknowledgment or permanent `4xx` (including invalid signature, malformed payload, amount mismatch, and event-ID collision), but finish all deliberate copies in the current round. A permanent rejection with no acknowledgment marks the provider event `failed` and resolves the Workmatic handler to avoid replay; Workmatic `done` then means processing finished, **not** delivered. Exhausted retryable errors leave the event `failed` and the Workmatic job `dead`. Record every HTTP submission, including concurrent duplicates, with a distinct attempt number. Mark the event `delivered` only after the planned copies finish and at least one received `2xx`; a crash before that mark can replay the round. A skipped event is `skipped` and creates no delivery job. No automatic or manual replay follows a terminal failure; the API's authenticated status lookup can recover the provider outcome.

Seed these exact active scenarios idempotently; snapshot each selected configuration on the payment so later seed changes do not alter an existing attempt:

| Code | Deterministic provider behavior |
| --- | --- |
| `PROVIDER_001` | Delay 30 seconds before initialization persistence. |
| `PROVIDER_002` | Return HTTP `500` before persistence. |
| `WEBHOOK_001` | Submit two concurrent copies with one event ID and identical body. |
| `WEBHOOK_002` | Submit three copies with one event ID/body, one second apart. |
| `WEBHOOK_003` | Schedule the webhook 15 seconds after provider completion. |
| `WEBHOOK_004` | Record provider completion and an event marked `skipped`; submit no webhook. |
| `WEBHOOK_008` | Pay-only: provider truth is success; deliver valid success first, then a separate valid failed event with a new event ID only after success is acknowledged. |
| `WEBHOOK_011` | Keep canonical event/provider amount; transmit a body with amount increased by 1,000 and sign those transmitted bytes. |
| `WEBHOOK_013` | Transmit the otherwise valid body with an invalid signature. |
| `WEBHOOK_016` | Transmit malformed JSON with a valid signature over those malformed bytes. |

For `WEBHOOK_011/013/016`, preserve the canonical provider outcome and original event separately from actual transmitted bytes. The API should reject the bad webhook, then may recover the **real** outcome through its periodic provider lookup. `WEBHOOK_008` tests that the API records a terminal-state conflict without reversing fulfilment. Client double checkout, client timeout, SSE disconnect, and API crash belong to those services' tests, not new provider scenario codes.

## 5. Logging, test gates, and acceptance

Use Pino with an AsyncLocalStorage request context. Generate or accept a validated request ID at ingress; log completion method, route template rather than token-bearing path, auth type/state, status, timing, and request/response sizes. Correlate initialization reference, provider reference, event ID, job ID, attempt number, scenario code, and redacted failure class. Never log service secrets, checkout tokens/URLs, signed bodies, personal data, or unbounded API responses. Emit counts or structured diagnostics for pending provider payments, due/failed/skipped events, Workmatic dead jobs, oldest undelivered event, webhook attempts, and SQLite storage pressure. The trusted-network diagnostic command/endpoint may expose counts but not payment secrets.

All required gates must pass before deployment. Use **Japa v5** (`@japa/runner` 5.x, not the legacy `japa` package) for unit, integration, contract, and Compose end-to-end tests. Pin an exact 5.x runner release and compatible `@japa/assert` and `@japa/api-client` releases in the Yarn lockfile after checking peer dependencies. Use a service-owned ESM `bin/test.ts` with Japa's `processCLIArgs`, `configure`, and `run`, launched by an ESM-compatible TypeScript executor supported by the pinned Node version. Define named `unit`, `integration`, `contract`, and `e2e` suites. `test` runs all suites; the four `test:*` scripts select their named suites through the same entry point. Keep `lint`, `typecheck`, and `build` separate. [Japa setup and suite selection](https://japa.dev/docs/installation).

Use Japa assertions and lifecycle hooks to provision/clean disposable file-backed SQLite databases, seed scenarios, and start Express on an ephemeral port for Japa API-client tests. Run migrations, same-file Knex/Workmatic concurrency, and worker retry/restart in `integration`; request/response, HMAC byte/signature, and API handoff fixtures in `contract`. Japa `e2e` drives real frontend/API/provider Compose containers with isolated volumes and browser automation; use a test proxy and actual child-process restarts for response-loss and crash windows. Keep browser assertions in that suite under Japa even if Playwright provides browser control. Do not mutate a developer's persistent data or share one SQLite file between independently running tests. Provide a command/result record and name every unrun suite. A passing build or unit suite alone is not acceptance.

| Test gate | Pass condition |
| --- | --- |
| Static/build | Lint, strict TypeScript check, production build, lockfile integrity, secret check, and Alpine container build pass. Native SQLite module loads in the runtime image. |
| Migrations/seeds | Real SQLite enforces unique references/event IDs/attempts, checks, foreign keys, WAL, and idempotent seeds. Workmatic tables initialize in the same file; startup fails for bad schema/path. No provider query uses another service's DB. |
| Auth/validation | API routes reject missing/wrong service token, bad reference, nonpositive/overflow amount, wrong currency, expired/out-of-range cutoff, unknown/inactive scenario, unknown fields, and malformed/oversize JSON. Browser routes reject invalid/expired tokens and extra outcome fields. |
| Initialization/recovery | New initialization returns `201`; exact replay returns `200` with identical provider reference/URL; changed details return `409`; concurrent duplicates create one row. `PROVIDER_001` initially times out/looks absent then resolves to one row; `PROVIDER_002` creates none; a test-proxy-dropped response is recovered by lookup. |
| Browser lifecycle | iframe and standalone page show authoritative amount, all allowed actions, accessible states, terminal idempotency, conflicting-action rejection, no completion after cutoff, and no token/path leak. Only an exact-origin `postMessage` hint is sent after commit. |
| Event integrity/outbox | Payment status and original event(s) commit atomically. Crash before enqueue recovers from the event outbox; crash after enqueue can duplicate delivery without duplicating provider outcome. Same-file Workmatic and Knex writers recover from bounded SQLite locks. |
| Webhook delivery | Exact-body HMAC, stable IDs/bytes, bounded timeout, attempt logging, 2xx stop, retryable error backoff/exhaustion, permanent 4xx stop, and restart/lease replay pass. Event `failed` is not confused with provider payment `failed` or Workmatic `done`. |
| Scenario matrix | Every seeded code produces its specified timing, duplicate count/order, skip, conflicting events, altered amount, invalid signature, or malformed signed bytes. The catalogue returns only active codes; payment snapshots remain stable after reseeding. |
| Contract/end-to-end | Real API/frontend/provider Compose flow covers success, failure, cancellation, iframe/new-tab fallback, duplicate webhook with one fulfilment, missing/bad webhook followed by status reconciliation, conflict incident, initialization timeout, provider outage, and isolated late-success discrepancy fixture. Assert provider and API DB states, delivery attempts, browser behavior, and logs. |

## 6. Deployment gates and rollback

Build one multi-stage image from an exact patch-pinned Alpine Node base and record its reviewed digest. Build native SQLite dependencies against the runtime Alpine/musl family. Run as non-root with only the provider DB volume writable. Keep HTTP browser/UI access on a browser-reachable trusted host-loopback origin while the API's service routes and outbound webhook target use the internal Compose network. Do not put the shared service or webhook secrets in the image or public frontend config.

| Gate | Requirement before proceeding |
| --- | --- |
| D1: configuration | Validate API callback URL, service/webhook secrets, provider public origin, frontend framing origin, DB path, worker/HTTP timeouts and lease ordering, and trusted host binding. No arbitrary outbound callback or public server-auth route. |
| D2: artifact | Reproducible Yarn build, exact Alpine patch pin/digest, native SQLite module load, non-root image startup, and static/unit/integration/contract gates pass. |
| D3: persistence | Verify local volume ownership, free space, SQLite-safe backup of an existing `payment_provider.db`, provider `up` migrations/seeds, and Workmatic schema initialization in that file. Never run production `down`. |
| D4: readiness | Start the one provider container; require internal liveness/readiness, expected schema/worker state, API-to-provider service authentication, browser payment-page access, and correct iframe framing. An API webhook outage is visible in diagnostics without losing durable provider outcomes. |
| D5: functional smoke | Initialize a payment, replay its reference, complete Pay/Fail/Cancel on separate attempts, inspect provider status and signed delivery, and verify the frontend refreshes from API state after the hint. |
| D6: recovery/scenario smoke | Exercise timeout-before-persistence, test-proxy lost response, duplicate/conflicting/bad/missing/delayed webhook behavior, API outage and restoration, event/job restart recovery, and browser expiry; verify one provider payment per reference and no API double fulfilment. |
| D7: operations | README explains local start/stop, migrations/seeds, configuration and origins, checkout/scenario walkthrough, test commands, request/event/job tracing, failed-event inspection, capacity/retention, SQLite backup/restore, and explicit disposable-volume reset. Record every gate result and unrun check. |

On failed rollout, preserve the provider DB and logs. Restore the previous image only if it can read the upgraded Workmatic and provider schemas; otherwise restore the verified pre-upgrade backup into an isolated volume before restarting the previous image. Never delete a persistent provider volume as rollback. The service remains a simulated provider: it does not collect card data or settle real funds.

## 7. Cross-service contract to verify before integration

The existing [API Service implementation document](API_Service_Implementation.md) and its checklist still name `POST /payments` and omit `checkout_expires_at`. Before integration acceptance, align them with `POST /payments/initialise`, the immutable expiry field, provider HTTP `500` as a retryable initialization result, and read-only `GET /payments/:reference` returning `404` until delayed initialization commits. This document records the dependency; it does not implement API Service changes. The frontend must keep treating the provider message as a hint and validate the `payment_url` origin as already specified in its own document.
